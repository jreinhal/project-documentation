SENTINEL Compliance Roadmap

Zero-budget path to production compliance | 2026-03-02 | Confidential

Guiding Principle

SENTINEL already has the technical compliance — air-gap, PII redaction, STIG audit logging, CAC/PIV, sector isolation, encryption. That's the hard part. What's missing is documentation, configuration hardening, and a few code changes to formalize what you've already built. Everything below is $0 out of pocket.

Coding Tasks You Can Start Now

These are concrete engineering tasks that move the compliance needle before any paperwork:

Task What to Do Compliance It Unlocks Effort
FIPS 140 Crypto Provider Replace default JCE with BouncyCastle FIPS provider. Add bcprov-fips and bc-fips to Gradle dependencies. Configure Security.insertProviderAt(new BouncyCastleFipsProvider(), 1) at startup. Add -Dorg.bouncycastle.fips.approved_only=true JVM flag. Ensure all TLS, hashing, and encryption operations go through FIPS-validated codepaths. FIPS 140-2/3 (required for ALL federal deployments) 1-2 days
FIPS Mode Configuration Flag Add sentinel.security.fips-mode=true/false property. When enabled: enforce FIPS provider, reject non-FIPS algorithms, log FIPS mode in startup banner. Wire into existing application.yaml profile system (govcloud profile enables by default). FIPS 140, FedRAMP, STIG 0.5 days
Session Timeout Enforcement STIG requires idle session timeout (typically 15 minutes for classified, 30 for unclassified). Add configurable sentinel.security.session-timeout-minutes property. Enforce in Spring Security session management. Add re-authentication prompt in frontend. STIG (SRG-APP-000295), FedRAMP AC-12 1 day
Failed Login Lockout You have LoginAttemptService already. Verify it enforces: max 3 consecutive failures, 30-minute lockout, lockout logged to audit trail. Add admin unlock endpoint. Configurable via properties. STIG (SRG-APP-000065), FedRAMP AC-7 0.5 days (verify + harden existing code)
Password Complexity Enforcement For STANDARD auth mode: enforce minimum 15 characters, mixed case, numbers, special characters, no password reuse (last 24). Store password history hashes. Add validation in StandardAuthenticationService. STIG (SRG-APP-000166), FedRAMP IA-5 1 day
Audit Log Integrity (HMAC Signing) You have IntegritySigner. Extend it to sign each audit log entry with HMAC-SHA256. Store signature alongside log entry in MongoDB. Add verification endpoint for audit log tamper detection. This proves logs haven't been altered. STIG (SRG-APP-000515), FedRAMP AU-10 1-2 days
Banner / Legal Notice on Login Government systems must display a DoD consent banner before login. Add configurable sentinel.security.login-banner property. Render banner on login page. User must acknowledge before proceeding. Standard DoD banner text is publicly available. STIG (SRG-APP-000068), FedRAMP AC-8 0.5 days
TLS 1.2+ Enforcement Verify and enforce TLS 1.2 minimum in Spring Boot embedded Tomcat config. Disable TLS 1.0, 1.1, SSLv3. Restrict cipher suites to FIPS-approved set. Add server.ssl.enabled-protocols=TLSv1.2,TLSv1.3 and explicit cipher list. STIG (SRG-APP-000014), FIPS 140, FedRAMP SC-8 0.5 days
Encryption at Rest Documentation + Verification MongoDB supports encryption at rest (WiredTiger + KMIP or local keyfile). Add a startup health check that verifies MongoDB encryption is enabled. Log warning if not. Add deployment guide section. HIPAA (164.312(a)(2)(iv)), FedRAMP SC-28, STIG 0.5 days
SBOM Generation in CI Add CycloneDX Gradle plugin to generate Software Bill of Materials on every build. Output SBOM to build/reports/sbom/. Iron Bank requires SBOM for every container image. Iron Bank, Executive Order 14028, FedRAMP 0.5 days
Container Hardening (Iron Bank Prep) Create a hardened Dockerfile based on registry1.dso.mil/ironbank/redhat/ubi/ubi9-minimal (or Chainguard). Non-root user, no shell, minimal packages, health check endpoint, read-only filesystem where possible. Iron Bank, STIG (container hardening guide) 1-2 days
Total coding effort: ~8-10 days. All of these are concrete PRs you can write today. The FIPS provider swap and SBOM generation are the highest-impact items — they're hard requirements that block federal deployment, and they're purely engineering tasks with no cost.

Phased Roadmap

Phase 1: Code Hardening (Weeks 1-2)

Engineering work that costs nothing but your time

CODE $0
  • Integrate BouncyCastle FIPS provider + FIPS mode flag
  • Enforce TLS 1.2+ with FIPS-approved cipher suites
  • Verify/harden failed login lockout (LoginAttemptService)
  • Add password complexity enforcement for STANDARD auth
  • Add configurable session timeout with re-auth prompt
  • Add DoD consent banner (configurable login banner)
  • Extend IntegritySigner to HMAC-sign all audit log entries
  • Add MongoDB encryption-at-rest health check
  • Add CycloneDX SBOM generation to Gradle build
  • Create hardened Dockerfile (non-root, minimal base image)

Outcome: SENTINEL can truthfully claim FIPS 140-validated cryptography, STIG-aligned session management, and Iron Bank-ready container packaging.

Phase 2: STIG Self-Assessment (Week 3)

Free tooling, documentation output

TOOL DOCS $0
  1. Download DISA STIG Viewer from public.cyber.mil (free, no account needed)
  2. Download the Application Security and Development STIG (the one that applies to web apps)
  3. Walk through every finding (there are ~280 checks):
    • Mark each as Not a Finding (compliant), Open (gap), or Not Applicable
    • For each "Not a Finding," document where in SENTINEL's code the control is implemented
    • For each "Open," decide: fix in code (add to Phase 1 backlog) or document as accepted risk
  4. Export the completed checklist as .ckl file — this is the standard format Iron Bank expects
  5. Store in repo at docs/compliance/stig-assessment.ckl

Outcome: A formal STIG self-assessment artifact you can hand to any government evaluator.

Phase 3: HIPAA Documentation (Week 4)

All documentation, no cost

DOCS $0

There is no "HIPAA certification." You self-attest by having these documents ready. HHS publishes the exact requirements at hhs.gov/hipaa.

  1. Privacy Policy — How SENTINEL handles PHI. Since it's self-hosted, the customer controls their data. Your policy documents what SENTINEL does and doesn't do with data at the application layer.
  2. Security Policy — Technical safeguards: encryption (at rest + transit), access controls (RBAC, sector isolation), audit logging, PII redaction, session management.
  3. Risk Assessment — Walk through the HIPAA Security Rule's 54 implementation specifications. For each, document how SENTINEL addresses it or marks it as customer responsibility (deployment-level control).
  4. Breach Notification Plan — Template for what happens if a breach occurs. Since SENTINEL is self-hosted, most of this is the customer's responsibility, but document what SENTINEL provides (audit trails, anomaly detection).
  5. Business Associate Agreement (BAA) Template — Standard legal template. Free templates available from HHS and NIST. Customize with SENTINEL-specific terms.

Store all documents in docs/compliance/hipaa/.

Outcome: Complete HIPAA compliance package. Medical edition customers can sign a BAA and deploy with confidence.

Phase 4: SOC2 Readiness Narrative (Week 5)

Self-documented controls mapped to Trust Service Criteria

DOCS $0

A formal SOC2 Type II report requires a paid auditor. But a SOC2 Readiness Document is free to produce and is accepted by many enterprise buyers in early-stage conversations.

  1. Create a spreadsheet or document mapping SENTINEL's controls to the 5 Trust Service Criteria:
    • Security — authentication, authorization, encryption, firewall rules, vulnerability management
    • Availability — uptime, disaster recovery, backup (customer-managed for self-hosted)
    • Processing Integrity — data accuracy, PII redaction validation, audit trails
    • Confidentiality — sector isolation, access controls, encryption, data classification
    • Privacy — PII handling, redaction, retention policies
  2. For each criterion, list the specific SENTINEL feature and code path that implements it
  3. Produce a customer-facing PDF: "SENTINEL Security & Compliance Posture"

Outcome: A document you can hand to any enterprise buyer asking "Do you have SOC2?" that demonstrates you take security seriously and have the controls in place. Graduate to a formal audit when revenue justifies it.

Phase 5: Go-to-Market Compliance Page (Week 5-6)

Public-facing trust signal

DOCS CODE $0
  1. Add a /security or /compliance page to SENTINEL's website/docs listing:
    • FIPS 140-validated cryptography
    • STIG-aligned security controls (with CKL available on request)
    • HIPAA-ready with BAA available
    • SOC2 controls documented (formal audit in progress / planned)
    • Air-gap deployment capable
    • CAC/PIV authentication (government edition)
    • Clearance-level sector isolation
    • PII detection and redaction
    • SBOM generated on every build
  2. Add "Security" link to main navigation

Outcome: Buyers and evaluators can see your compliance posture before even contacting you. This is what enterprise/gov procurement teams look for first.

Phase 6: Outreach (Week 6+)

Revenue-generating activities that cost nothing

OUTREACH $0
  1. Carahsoft — Email their ISV partnerships team. Pitch: "Self-hosted RAG platform with air-gap deployment, CAC/PIV, STIG audit logging. No competing product in your portfolio." They take a rev share, not upfront fees.
  2. Platform One / Iron Bank — Join the Platform One community at p1.dso.mil. Submit a "Party Bus" request to get your container into Iron Bank. Having the hardened Dockerfile and SBOM from Phase 1 gets you in the queue.
  3. AWS Marketplace — APN registration is free. Start packaging an AMI. List with BYOL (Bring Your Own License) pricing model — zero cost to list.
  4. Find a pilot customer — One government user running SENTINEL on their network, even unfunded, is worth more than every compliance document combined. Check LinkedIn for government innovation labs, CDOs (Chief Data Officers), and AI/ML program managers.
